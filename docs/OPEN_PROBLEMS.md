| OP-01 | RESOLVED (verified on a live recording, 1 Oct 2026) | Replay of live recordings was not faithful. | Root causes (CL-08): concurrent stages stored results in completion order (source, passage and claim ids, event order, duplicate ownership); timeout retries took fetch budget in a timing-dependent order, so a replay (instant, sequential) fetched URLs the live run never did; a retry that succeeded overwrote the recorded timeout. Also, the old recordings were made with indented JSON and K=6, so they cannot replay under the current defaults at all. Fixed and covered by `tests/unit/test_replay_fidelity.py` (record with jittered providers, timeouts and tight budgets, replay, compare every event and the stored tables). **Verified 1 Oct 2026:** one live run recorded with this code (`docs/benchmarks/canon-b3-o3.json`, recordings in local `cache/recorded_canon1`) replayed offline with provider keys blanked via `scripts/replay_check.py`: all 307 events and the sources (44), passages (418), claims (58), coverage (20) and conflicts (6) match the live run row for row. A live run that ends on the wall-clock soft limit cannot replay faithfully (time is not recorded). |

| OP-03 | OPEN, analysed | Every live run ends on the search budget. | Structural: 10 round-0 tasks x 2 queries = 20 searches (FR-04 floor, B-12), leaving 4 for one follow-up round. `scripts/search_budget_analysis.py` on the 3 canonical recordings: query #2 of each task (12 of 24 searches) stored 6, 2 and 5 of 48, 47, 48 sources and 1, 1 and 0 useful ones (`sources_per_task=4` is filled by query #1's 6 hits and query #2 is a token reorder of query #1); the 4 round-1 searches changed no coverage cell in any of the 3 runs. | OP-04 | OPEN | Extractor dominates LLM cost and call count. | About 100 calls per run, one per (source, slot), about 85 percent of input tokens. The large saving needs a prompt/schema change (several slots per call), not done here. **Update:** batching is implemented behind `SARVAM_EXTRACTOR_BATCH_SIZE` (default 1, B-33/CL-09); it has not been measured, so no cost or quality effect is claimed. Ready for a benchmark with `make benchmark-llm` (`extractor_batching` in its output). Re-record the canonical runs first, since the prompt text changed (CL-09). **Measured 1 Oct 2026 (n=3 each, live Gemini):** batch 1 (new prompt) 299k tokens / 126 calls; batch 2 235k / 88; **batch 3 153k / 49 (-46 percent tokens, -57 percent calls vs the 286k / 115 baseline)**, wall 131 s vs 176 s. Slots per source average about 3, so sizes above 3 will save little. **Zero-credit follow-up:** 43 percent of fetched sources yield no claim and carry 47 percent of extractor passages, but page-level heuristics (number density) cannot separate them. `scripts/extractor_gate_analysis.py` (offline, 651 jobs from 8 stored runs): other-slot jobs yield 13 percent (58 of 436) vs 46 percent for the source's own slot (99 of 215); a floor of `own slot, or best-passage query-word overlap >= 3` would skip 162 of 651 jobs (about 21 percent of passages) and lose 6 of 157 yielding jobs (4 percent). **Implemented opt-in, default off (B-35, CL-10):** `SARVAM_EXTRACTOR_MIN_OVERLAP=3` gates only a source's other slots; unit-tested offline. Its effect on coverage and stop state is NOT measured (needs a live run), so the default stays 0. **First live run with batch 3 + floor 3 (n=1, `canon-b3-o3`):** 53 calls, 155k tokens, 138 s, SUFFICIENT_WITH_CAVEATS, coverage 8 GREEN / 1 AMBER / 1 RED, 57 supported claims, report verified with 0 dropped sentences. The floor cut extractor work (87 slots over 31 calls vs about 108 slots over 36 calls in the batch-3 runs) but total tokens stayed level with batch 3 (153k), because more claims meant 12 verifier and 6 explainer calls; one run cannot separate the floor's effect from noise. |
