# Decisions and change log

ADRs 101-111 are defined in SSOT section 20 and are not duplicated here. Bootstrap-time decisions that
the SSOT leaves open are logged below. From hour 1 of the build, any change to contracts, the schema,
thresholds or the cut list requires a row in the change log and an update to the affected section in
the same commit (SSOT section 21).

## Bootstrap decisions

| ID | Decision | Reason |
| --- | --- | --- |
| B-01 | Product is named Sarvam; "ResearchOps" is used only for the challenge domain and the SSOT title. | Product identity. |
| B-02 | Bun workspace at the repo root (`frontend` only); Python via uv with `package = false`. | Bun-only JS tooling; backend is not a distributable package. |
| B-03 | `Run.status` values: queued, running, completed, failed. `SourceStatus`: found, fetched, SOURCE_UNAVAILABLE, SOURCE_EMPTY. | SSOT lists the columns but not the enum values; derived from section 18. |
| B-04 | `events.id` is an integer autoincrement so it can serve as the SSE `Last-Event-ID`. | SSOT requires Last-Event-ID reconnect. |
| B-05 | Contracts use `extra="forbid"`. | Prevents silent shape drift between backend and frontend. |
| B-06 | Schema versioning via `PRAGMA user_version` + idempotent `schema.sql`. | Simplest migration strategy for a 24-hour MVP. |
| B-07 | `uv.lock` is not committed. | CLAUDE.md rule "no dependency lockfile other than Bun's"; reversible (see final report). |
| B-08 | `controller.run_m0` is a minimal linear M0 driver, written as part of T07; T14 extends or replaces it. | No task card owns the M0 wiring, but G1 needs an end-to-end run before Stream B lands. |
| B-09 | Short ids (S3, P12, C41, ...) are allocated globally monotonic by `backend/store/ids.py::next_id` inside `BEGIN IMMEDIATE`; origins, dimensions, slots and tasks stay per-run. | `schema.sql` keys most tables globally, so ids would collide across runs. No schema change. |
| B-10 | The run task and each SSE stream open their own SQLite connection; `busy_timeout=5000`. The lifespan connection serves short request handlers only. | One shared connection is unsafe with concurrent writers and readers. `POST /runs` is `async def` and does a few sync SQLite calls on the event loop (acceptable for the MVP). |
| B-11 | SSE frames carry `id:` and `data:` only (no `event:` field); heartbeat is a `: keepalive` comment every 15 s. | `EventSource.onmessage` does not receive named events. |
| B-12 | Planner is limited to 4-5 dimensions x 2 slots x 1 task; discover uses exactly 2 queries per task (16-20 searches in round 0 against MAX_SEARCHES=24). | FR-02 plus FR-04 can exceed the budget in round 0. The default cap is not changed; G1 measures and reports. |
| B-13 | Gateway retries LLM HTTP 429 up to 3 times, honouring `Retry-After` (capped at 30 s); per-role `max_tokens` are 3000-6000. | Groq free tier allows 8,000 tokens per minute for `gpt-oss-120b`; unhandled 429s failed the live planner test. |
| B-14 | Quote guard keeps SSOT 9.4 (exact substring or partial ratio >= 0.95) and adds two rejections only: fewer than 4 words, and a fuzzy match must contain every number the quote states. | One altered digit scores about 0.97 on a short quote, which would let a changed price pass. Never loosens the guard. |
| B-15 | An extractor call is made per (source, relevant slot): own slot first, then other slots sharing content words, at most 3 slots per source. | Keeps LLM calls inside MAX_LLM_CALLS=250. The cap of 3 is a backend constant, not an SSOT value. |
| B-16 | A task whose searches all fail is marked `blocked` and a second `task.started` event carries the typed reason ("Task blocked (RATE_LIMITED): ..."). | No event type exists for task failure and none may be invented; reducers already key on task id. |
| B-17 | If the writer fails or the budget is exhausted, the report is rendered evidence-only (each verified claim cites itself) and says why. With no eligible claims the writer is not called. | Wrap-up must still produce a cited report (SSOT 7.1). |
| B-18 | M0 claims stay `pending` with `quote_verified=1`; the writer accepts them via `writer.eligible_statuses()`. Quote-guard rejects are events only. | No judge exists before M1 and `claims.passage_id` is NOT NULL (decision D6). |
| B-19 | LLM 429s with no `Retry-After` wait 5, 15, 30 s (cap 60 s) and a Google-style `retryDelay` in the error body is honoured. The live setup uses Gemini through its OpenAI-compatible endpoint with `SARVAM_LLM_CONCURRENCY=2`. | Gemini free tiers limit requests per minute (10-15), so short retries would fail. No new environment variable. |
| B-20 | LLM calls also retry transient provider overload (HTTP 500/502/503/504) with the same 5, 15, 30 s backoff; other 4xx are not retried. Strong model pinned to `gemini-3.6-flash` (3.7 and 3.8 returned 503 "high demand", 2.5 Flash returned 404 for new users). | Gemini capacity spikes are common and would otherwise fail the planner and end the run. |
| B-21 | A verdict sets the claim status: `supports` -> supported, `partial` -> partial, `contradicts` and `irrelevant` -> rejected (verdict kept in `evidence_links`, claim excluded from `/state` and from the writer). `contested` is never set by the judge: it marks members of an open numeric conflict (SSOT 9.11) and is derived by conflict detection on every pass. Supersedes B-18 for claim eligibility: the writer accepts only supported, partial and contested claims. | SSOT 9.5 and 9.11 use `contested` for open conflicts, FR-10 keeps only supports and partial as evidence, FR-18 requires verified claims. |
| B-22 | Numeric conflicts: relative difference is `abs(a-b) / max(abs(a), abs(b))` against `conflict_tolerance` (0.15, inclusive). Claims are compared only within one slot, same attribute, same entity (equal words, or the shorter entity of at least two words contained in the longer) and same normalised unit and period; only claims judged `supports` take part. Values within tolerance form one *position*; one conflict row is stored per pair of positions, represented by the most primary claim on each side. Period is converted to per month only for currency values. Dimension rollup with no critical slot uses the lower median. | SSOT 9.7 and 9.8 leave these open; symmetric difference and one row per disagreement keep the matrix and the conflict list readable (3 planted conflicts = 3 rows). |
| B-23 | Unit traps are classified by rule, not by the LLM: claims that differ as written (69 per day, 2,070 per month) but agree after normalisation become a `unit_error` conflict, `explained`, with a generated explanation. Only disagreements that survive normalisation go to the conflict explainer; a verdict other than `genuine` without an explanation stays open; if the explainer fails the conflict stays open and is retried next pass. | SSOT 16.2 F09 and T11 require the trap to be visible and explained without downgrading the cell; conflict classification stays deterministic where the evidence is structural (rule 7). |
| B-24 | Origin clustering details left open by SSOT 9.6: registrable domain uses the last two labels except under a listed set of public multi-part suffixes (no new dependency); the syndication-network list is a short starter list in code; S3 needs the same value for the same claim key and a shared six-word sequence with at least four content words; S4 attribution entities must start with a capital letter and are matched to a retrieved publisher by brand label, else become an origin labelled with the entity. A multi-member origin stores the method by priority domain, near_duplicate, shared_number, attribution. Origin ids are stable across rounds (an origin keeps its id while a cluster still contains its members). | Needed to make S1-S4 deterministic and testable; an origin row holds one method value. |
| B-25 | The verifier (`verifier.v1`) gets only the claim text and the passage, about 5 pairs per call, and is asked once more for pairs the model skipped. Claims still unjudged after that stay `pending`, are not evidence, and raise a `budget.warning` (`verifier_unverified_claims`). It uses the FAST tier like the extractor; a separate verifier model (SSOT 9.5 "prefer a different model") is not added because it needs a new environment variable. | FR-10, FR-18, NFR-04; no new configuration without need. |
| B-26 | `run_m0` now also runs VERIFY and ANALYZE. On any wrap-up the ANALYZE phase still runs without LLM calls (conflicts unexplained stay open) so the matrix and the future stop state reflect the gaps (SSOT 7.1). The INR rate table in `backend/intel/numeric.py` is an approximate, dated default (`INR_RATES_AS_OF`), to be refreshed before figures are treated as exact. | G2 needs a matrix from a real run; T14 will replace the linear driver. |
| B-27 | Stop policy details left open by SSOT 9.10: a challenge round is *complete* when it has attacks and every attack has an outcome; a round whose challenger failed or returned no valid attack is not complete, so the stop card says the challenge was not completed. When the sufficiency criteria hold the reason is always `criteria_met` (the table pairs it with SUFFICIENT), even if a hard limit hit at the same time. Order of end conditions after a round: hard limit, criteria met, zero marginal gain after a completed challenge, round limit. "Open material conflict" is any conflict with status `open`. `recompute_stop` rebuilds the decision from the stored tables and `runs.termination_reason`. | SSOT states the table but not these edge cases; they make the decision a pure, recomputable function. |
| B-28 | The search budget pays for whole tasks: before a follow-up round the controller computes how many tasks the remaining searches allow (`queries_per_task` searches each), gives the challenge up to `min(3, max(1, capacity // 2))` attacks and the rest to gap tasks (RED critical slots first). No capacity left ends the run as `budget` with the challenge not completed. | Round 0 already uses 16 to 20 of the 24 searches (B-12); unpaced follow-up tasks made every run end in a mid-round budget error. |
| B-29 | Each attack becomes one `challenge` task using its first follow-up query (discover adds the differently phrased second query); the second query is not searched. Challenge outcomes are decided by the verifier on the top 6 passages, ranked by word overlap with the attack, of the sources that task found; a verifier failure leaves the challenge without an outcome unless a supporting verdict already decided it. | Keeps a challenge within about 2 searches and 2 verifier calls; SSOT 9.9 does not say how many passages are examined. |
| B-30 | `run_m0` is replaced by `controller.run_research` (round loop, stop policy; supersedes B-08). CLAIMS is delta-only by processing sources whose task belongs to the current round (FR-16); DISCOVER, ACQUIRE, EXTRACT and VERIFY were already delta-only. `synthesize` and its events carry the final round number. | T14; without the round filter every follow-up round re-sent old sources to the extractor. |
| B-31 | Report verifier (FR-19, FR-20): a findings sentence is removed (and listed in `dropped_sentences`) when it cites no stored claim, cites an unknown claim or dimension, or contains a number that none of its cited claims states; numbers are compared normalised (`1,299` = `1299`) against the claim text, quote and value, plus numbers in the user's own question and scope. Summary sentences are checked against all eligible claims. Labels: `contested` if any cited claim is in an open conflict, `supported` if every cited claim's slot is GREEN, otherwise `single-origin`; `assumed` is not produced because the writer has no "System inference" output yet. The report gains coverage, conflicts, "what could change the conclusion" and the assurance state, and is stored with `certainty_state` = the final state. | SSOT 9.11 defines the labels by coverage state; the fourth label needs a writer contract change that is not on the G3 path. |
| B-32 | LLM optimisation (measured, see `docs/LLM_OPTIMIZATION_REPORT.md`): compact JSON payloads are the default (`SARVAM_LLM_COMPACT_JSON`, default 1) and the extractor sees the top 5 BM25 passages (`Thresholds.passages_per_slot_source` 5, was 6; `SARVAM_PASSAGES_PER_SLOT`). Per-role output ceilings, verifier batch size (`SARVAM_VERIFIER_BATCH_SIZE`, default 5) and LLM concurrency are unchanged. Budget semantics are documented, not changed: `max_llm_calls` counts validation attempts (every request that reaches the provider path through `gateway.llm`), not logical operations and not 429/5xx provider retries. Cost counts provider-reported cost, else a local estimate from `SARVAM_LLM_PRICE_FAST/STRONG` (USD per 1M tokens, unset by default), else is *unavailable* and not counted; the first unavailable call raises a one-time `budget.warning` with limit `cost_unavailable`. | The extractor is about 100 of about 115 calls and 85 percent of input tokens per run; measured n=2 to 3 live runs per config. Lower output ceilings (planner 1800) truncated the planner and failed both runs. MAX_COST_USD cannot be enforced honestly without a cost or a price. |
| B-33 | Extractor batching is opt-in (`SARVAM_EXTRACTOR_BATCH_SIZE`, default 1). With N > 1 the slots of one source (own slot first, at most 3, B-15) are split into batches of N; each slot keeps its own top-K BM25 passages, the call carries their union once, and code checks every claim's `slot_id` is in the batch and its `passage_id` was ranked for that slot (`slot_not_in_batch`, `passage_not_allowed_for_slot`, both `claim.rejected`). Size 1 sends the pre-batching payload unchanged. | Cuts extractor calls per source without a new claim schema (ClaimDraft already has `slot_id`). Not measured yet. |
| B-34 | `cache/` (recorded provider and LLM responses) is local-only: git-ignored, never committed, no `.gitkeep`. `RecordReplay` creates `cache/recorded` on first write. The per-slot extractor cap stays 6 (`MAX_CLAIMS_PER_CALL`), enforced per slot in batches. Canonical recordings are generated locally after the final configuration is chosen (T25). | Recordings are generated evidence and go stale whenever a prompt or payload changes (keys hash the messages). G0 now asserts that nothing under `cache/` is tracked and that `cache/` is ignored. | |
| B-35 | Extractor relevance floor is opt-in (`SARVAM_EXTRACTOR_MIN_OVERLAP`, `Thresholds.extractor_min_overlap`, default 0 = off). When N > 0, an extractor job for a source's OTHER slot (not the slot whose task found it) is skipped unless the slot's words overlap the best ranked passages in at least N words; the own slot is never gated and still needs one shared word. Skipped slots simply get no extraction, so coverage shows them as unfilled as before. | `scripts/extractor_gate_analysis.py` on 651 stored jobs: other-slot jobs yield 13 percent vs 46 percent for the own slot; N=3 skips 25 percent of jobs (about 21 percent of passages) and loses 4 percent of yielding jobs. Effect on coverage and stop state NOT measured. | |
| B-36 | Accounts and an admin role are now in scope, superseding the "auth, multi-user" exclusion (SSOT 2 and 20, `CLAUDE.md` rule 5). This also retroactively records the stdlib auth already in `backend/auth.py` (PBKDF2 passwords, hashed 7-day bearer sessions). `users.role` is `user` or `admin`; admins are promoted only by the `SARVAM_ADMIN_EMAILS` environment variable at register or login, with no default credentials. `/api/admin/*` is read-only in Phase 1 and gated server-side by `require_admin` (401 anonymous, 403 non-admin). Anonymous `GET /runs` lists only unowned runs, and `POST /runs/{id}/stop` on an owned run needs its owner or an admin. | The operator console needs a real role. The auth code shipped without an ADR, and anonymous `GET /runs` leaked every user's runs. | Additive; local single-host use remains the deployment model. |
| B-37 | Admin management (Phase 2/3). Actions: change role, disable or enable, set a per-user cost quota, delete a user (runs are anonymised), stop a run, hide or unhide a run, edit the default run budget, export runs and costs as CSV. Rules: you cannot demote, disable or delete yourself, and the last enabled admin is protected; a rejected action writes nothing. Quota is checked when a run is created, against metered cost in `events.cost_usd` (a provider that reports no cost is never limited by it). Hiding is soft: the run, its events and its cost stay. Admin actions are recorded in a new append-only `admin_actions` table, not in `events`, because `events.run_id` is a required foreign key and user and settings actions have no run. A user listed in `SARVAM_ADMIN_EMAILS` is re-promoted at their next sign-in, so demoting such a user has no lasting effect. The preset admin is created with `python -m backend.admin.seed` (random password, printed once). CSV cells starting with `=`, `+`, `-`, `@`, tab or CR get a quote prefix. | Phase 2 and 3 of the admin portal plan. | Schema v4; CORS now allows PATCH, PUT and DELETE (profile update and account deletion were blocked cross-origin before). |
